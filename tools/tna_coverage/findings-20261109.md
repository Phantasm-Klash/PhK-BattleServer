# TNA 1.40 bulletFunc 逐弹对齐记录（2026-11-09）

门禁：`bash tools/tna_coverage/run.sh` → **MATCH 79 / MISMATCH 0 / RNG_DIFF 0 /
MISSING 0 / UNKNOWN_REF 7**；`ctest --test-dir build-linux` 20/20。

基准不再是人工翻译的 `bullet_funcs_reimpl.hpp`，而是 `tna_emu.py` 用 unicorn
**直接执行 `libMyGame_arm64.so` 里的原版 bulletFunc 本体**，逐 tick 导出状态。
79 个有独立符号的函数全部与生产 `UpdateBulletMotion` 逐字段一致。

## 1 基准工具本身的三处修正（都会改变「真值」）

1. **单精度 sin/cos**。原版 `MyMathUtil::sin/cos` @`0x5ab0c0/0x5ab0dc` 是
   `sinf/cosf(deg * 2π(float) / 360.0f)`，两步都是 float。旧 hook 用 Python
   `math.sin(math.radians(deg))`（double），在 func36 的 `fcvtzs w8,s0,#7`
   （×128 截断）边界差 1（192 vs 191）。改用 `libm.so.6` 的 `sinf/cosf` 后
   func36 转绿且 79 函数零回归。
2. **每个 func 从零初始化对象开始**。旧模拟器复用同一块假对象内存，
   `bulletLoop(0x58c)`、`spdAcc(0x574)` 等未列进 init 的字段带着上一个 func
   的残留；func74 因此被误判（残留 `bulletLoop>=1` 走了 `setOpacity(life)`）。
   现在 `run_func` 每次 `mem_write(OBJ, b"\x00"*OBJ_SIZE)` 再写 vptr。
3. **`MyMathUtil::random` 与生产共用同一确定性 RNG**。PLT `0x2f7860` 未拦截时
   会 `br x17` 到 0，返回的是寄存器垃圾（func62/70 出现 `angle=1719003776`
   这类值）。原版走 `arc4random`，不可复现；本项目用 `DeterministicRng`
   （FNV-1a + Mix32，输入 seed/tick/func/spawn + counter），基准侧以
   `_DetRng` 逐位等价实现并拦截该 PLT，含随机分支的 func 才可比。

> 这三条都属于「把基准做得更忠实」，不是放宽容差或改判据。

## 3 本轮修正的 20 个 bulletFunc（共性问题：缺门控 / 多写字段）

- **多写了 speed/speedCap**：func1 三段独立反弹完全不写速度（旧实现写
  `spdInit2=-1` 导致倒飞），每段命中 `life--`；func7 四段同理，且 y 段 C=360。
- **缺门控**：func13 `dist² >= life²` 跳过 + ±2° 限速；func38 `p2<1` 门 + 节拍；
  func48 蓄力 30 帧（期间只 `speed=0`）；func50 三阶段状态机（40/80 常数写反了）；
  func58 节拍 `t1%life`；func67 `life<1` 整段跳过；func31 `life>=1` 查表。
- **把 setRotation/贴图参数误当运动量**：func58（`360-angle+90` 只改贴图朝向）、
  func82/83（参数方程是 `setPosition` 的**绝对坐标**，原版不写 angle/speed）。
- **状态机真值**：func18 用 `p2` 存上次瞄准角；func39/func48/func50/func67
  的复位段是 `0x598` 起 16B 整体拷贝到 `0x568`（angleAcc/f56c/v/spdAcc）。
- **按 life 查表**：func31（31 档 hitDis / bulletType，实测 2.4/3/3/43/2.4/2.4…）。
- **签名带 Vec2 入/出参**：func20 与 func62 通过 `x8` 缓冲直接改写位置；
  func62 另按 `life>=1` 分两族（折返到 `-cw`/`40-ch` vs 只改 angle）。
- **三段出屏反射**：func70 每段 `C-angle+random(-p2,p2)`、按 p1 五档换皮、
  末尾 8B 拷贝 `{spdInit2,xacc}→{speed,spdAcc}`、`life--`；第三段 C=360 且不归一。

## 5 追加：基准升级为「执行原版 update 完整一帧」→ 86/86

上面的 79/79 仍是「独立 bulletFuncN 符号 + 手工复刻尾段」口径。解码
`EnemyBullet::update` 后发现**符号表不是分派表**，真值应来自整帧执行：

- 跳转表 @`0xb0a88e`，表项 `uint16 × 4` + 基址 `0x50b514`，85 个编号 →
  66 个入口；20 个落共用出口 `0x50c618`（rotateFlg 尾 + funcNo 比较链）。
- 二次分派表 @`0xb0a938`（funcNo 26..83）：26 走参数方程 setPosition，
  33/37/51/66/75/81/82/83 `bl` 独立 func 后**跳过位置积分**，其余走
  `50cc5c` 默认 `pos += (vx,vy)`。
- 速度合成尾段 `50ca58` 之前有 `50c8f0` 的 **`speed += spdAcc` 并夹到
  speedCap**；func3 / 29 / 47 写完后直接 `b 50cafc`，**跳过速度合成**。
- 9/10/49/56/59/68/69 没有独立符号：整帧实测 9/10/49/56/68/69 为默认
  直线，59 在 `t1<life` 时每帧 `angle += 1`（共用出口内联分支 `0x50c768`）。

★ 由此推翻两条旧结论：① func3 的 vx/vy **不会被尾段覆盖**（原版跳过
合成），整帧实测 vx=0.0163；② func82/83 的 setPosition 后**不做位置积分**
（x=320/164，不是 323/167）。此前 79/79 属于「基准和生产一起用错尾段」
的自洽假象。

**整帧执行实现**（`tna_emu.py --mode update`，默认）从分派点 `0x50b4e8`
跑到 `ret`，需要：拦截 `bl bulletFuncN@plt` 并重定向到真实函数体、
`x23` 指向可控零内存（否则 `[x23+40]` 读到 ELF 头触发 `__stack_chk_fail`）、
`[sp+0x30]` 放当前位置 Vec2、`ldp x29,x30,[sp,#144]` 是**成对加载**所以
返回地址要写在 `sp+152` 而不是 `sp+144`。保留 `--mode func` 作旧口径对照。

生产端相应补齐：尾段的 accel 应用 / 跳过速度合成 / 跳过位置积分（用
预减位移抵消宿主固定的 `pos += vx,vy`）；func1/7/11/62/70 的 life 门；
func4/5/27 的内联门控（整段 no-op）；func11/29/39/46/47/58/59 的 update
内联真值。门禁：`run.sh` **MATCH 86 / 0 MISMATCH / 0 RNG_DIFF /
0 UNKNOWN_REF**，`ctest` 20/20。
